The propose, review, approve loop

Minerva talks to a graph-backed knowledge base, and the one design decision that makes that safe is simple to state and easy to underestimate: the model never gets to write to it directly. Every AI-originated change to .minerva/graph.ttl — a new claim, a rewritten note, a proposed source summary — has to pass through a single choke point, the approval engine, before it becomes real.

The Trust Principle

The LLM proposes, the human confirms. Conversation output is evidence to be evaluated and filed, not an authoritative update to the graph. This is the most important design decision in Minerva — not a safety feature bolted on afterward, but the reason the approval engine (src/main/llm/approval.ts) exists at all.

Why proposals exist

An LLM is a source of claims about your notes, not an editor with commit rights. Treating its output as evidence means every graph mutation it wants to make is a suggestion until you look at it — so wrong claims, bad links, and hallucinated components stay quarantined as pending records instead of silently becoming part of what you know. The mechanism for that quarantine is a node type: thought:Proposal, with a thought:proposalStatus of thought:pending, thought:approved, thought:rejected, or thought:expired.

Internally, every LLM apply path funnels through one function, proposeWrite(), which takes an operationType (what kind of change this is) and a bundle of payloads (what it would actually write). It always does the same thing: file a pending thought:Proposal and stop. Nothing lands until you approve it.

Everything is a proposal

There are no trust levels to learn — no writes that skip review. Whatever the model emits — a new claim (new_claim), an evidence link (evidence_link), a component (component_creation), a note move or rename (note_refactor), a delete (note_delete), an in-place rewrite (note_rewrite), or proposed source properties (source_properties) — proposeWrite() writes a thought:Proposal with status pending and applies nothing until you act on it. The operationType is just a label on the review card; it never changes whether you get to review.

This holds even for changes that feel automatic. Auto-tagging a note, for example, still files an ordinary note_rewrite proposal — it simply self-approves it the moment you accept the suggested tags on the conversation card, so the write lands with a real approved proposal behind it rather than slipping in unrecorded. Every graph write the LLM makes has a proposal you can find in the Proposals panel.

The diff view

A pending proposal isn't a one-line description you have to trust — it's the literal payload bundle waiting to be applied, and reviewing it means reading that payload directly. Each payload in the bundle carries enough to reconstruct exactly what will land:

  • A note payload carries the full content of the file that would be created (plus the relativePath it would be filed at) — you read the whole note, not a summary of it.
  • A graph-triples payload carries the raw Turtle that would be merged into the store, along with the affectsNodeUris it introduces — the same triples the trust-integrity query later checks for approval provenance.
  • A note-rewrite payload carries the full replacement content for an existing note; approval captures the prior content as a pre-image first, so the operation is reversible even though what you're shown is the new version.
  • A note-delete or note-refactor payload names the path (or fromPath/toPath) being removed or moved.

A proposal can bundle more than one payload, and the bundle is atomic: approving applies every payload in order, rejecting discards all of them, never half. This is the same mechanism the Proposals panel renders as an expandable card per payload — that page documents the panel's UI in detail (the status tabs, the keyboard shortcuts, the project-wide scope); this page is about what makes the payload trustworthy to read in the first place: it's the actual write, not a paraphrase of it.

Approving and rejecting

Once you've read the payload, the decision is one keystroke: y to approve, n to reject, both handled by approveProposal() / rejectProposal() in approval.ts. Approving applies the bundle and flips status to approved; rejecting flips status to rejected and applies nothing, but the proposal node itself stays in the graph either way — reviewed history, not a queue you empty. See Proposals for the full keystroke reference, the status-tab filtering, and what the panel shows you while a card is collapsed.

Auto-expiry

Every proposal is stamped with an autoExpires timestamp at creation — seven days out by default (write.expiryDays ?? 7), configurable per write. There is a real function that enforces it, expireProposals(), which walks every still-pending proposal past its autoExpires date and flips it to expired.

What doesn't exist is anything that calls that function on a schedule. expireProposals() is wired to a single IPC channel, proposal:expire, exposed on window.api as api.proposals.expire() — but nothing in the renderer currently invokes it, and there's no timer in main running it in the background. In practice a proposal past its expiry window doesn't flip itself to expired; it just keeps showing as Pending until something calls that IPC method, which nothing currently does. Treat autoExpires as a recorded intent rather than a guarantee — Proposals covers this same finding from the panel's side.
